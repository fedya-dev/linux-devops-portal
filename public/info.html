1. Frontmatter

Всеки файл започва и завършва с ---.

---
title: "Заглавие на статията"
description: "1-2 изречения — показват се в листинга и в Google"
pubDate: 2026-09-12
category: "DevOps"
tags: ["Tag1", "Tag2", "Tag3"]
author: "LinuxDev Team"
featured: false
readTime: "12 мин"
heroImage: "/images/category/slug.webp"
heroImageAlt: "Alt текст за картинката"
---
ПолеЗадължителноОписание
title✅Заглавие на статията
description✅1–2 изречения за листинг и SEO
pubDate✅Дата във формат YYYY-MM-DD
category✅Една от шестте категории: Linux, DevOps, Technologies, Security, Cloud, Tools
tags❌Масив от тагове, показвани като badge-ове
author❌По подразбиране „LinuxDev Team“
featured❌true, ако статията е във featured секцията
readTime❌Приблизително време за четене
heroImage❌Път в public/images/..., започващ с /
heroImageAlt❌Alt текст за картинката
Важно: category трябва да бъде точно една от шестте категории, а pubDate — само дата без час.

2. Структура на съдържанието

След затварящия frontmatter следва Markdown съдържание по тази схема:

## Защо [темата] има значение
(въведение — какъв проблем решава темата)
## 1. [Първи съвет/секция]
(обяснение + пример)
## 2. [Втори съвет/секция]
(обяснение + пример)
## Заключение
(обобщение, без повторение на изброеното)

3. Правила за форматиране

  • ## за основни секции, ### за подсекции.
  • Код в блокове с изричен език: bash, dockerfile, yaml, python.
  • Inline код с обратни кавички: code.
  • Списъци: - за неподредени и 1. за подредени.
  • Bold — пестеливо, само за истински важно.
  • Връзки само когато реално добавят стойност.
  • > за важни бележки и предупреждения.

4. Стил на писане

  • Чист български език с минимум англицизми в прозата.
  • Професионалната терминология остава на английски: caching, layer, build context.
  • Директен, честен и топъл тон без излишни клишета.
  • Точността е по-важна от звученето — непровереното се отбелязва ясно.
  • При по-добър или по-безопасен подход той се предлага веднага.

5. Тестване локално

npm run dev
  • Провери конзолата за грешки.
  • Изпълни npm run build и провери дали build-ът приключва чисто.
  • Провери всички връзки с link checker.
  • Провери schema-та с Rich Results Test, ако има structured data.

Съдържание, страници и компоненти

Статиите се намират в src/content/posts/*.md, а уроците — в src/content/tutorials/*.md. Schema-та за колекциите е в src/content.config.ts.

Основни маршрути

  • / — src/pages/index.astro
  • /blog и /blog/<slug>
  • /tutorials и /tutorials/<slug>
  • /linux, /devops, /technologies, /security, /cloud, /tools
  • /404 — страница за липсващи адреси

Компоненти

PostCard, TutorialCard, Header, Footer, Badge, SafeImage и CodeCopy се намират в src/components/.

Инфраструктура

Sitemap-ът се генерира от @astrojs/sitemap. Допълнителните файлове са public/robots.txt, public/llms.txt и public/favicon.svg. Hero images се съхраняват в public/images/<category>/.

Ежедневен workflow

# 1. Пишеш нова статия
nano src/content/posts/моята-статия.md
# 2. Тестваш локално
npm run dev
# 3. Проверяваш build
npm run build
# 4. Пушваш
git add .
git commit -m "Add article: заглавие"
git push
  1. Изчакай 1–2 минути и провери GitHub Actions.
  2. Отвори https://linuxdev.fedia.eu/blog/моята-статия.

Синхронизиране

Преди работа на домашния компютър или работния лаптоп отвори терминала в папката на проекта и изпълни:

git pull

Така ще свалиш промените, качени от другото устройство, и работната папка ще бъде синхронизирана.
